What's in the data
Every number on this dashboard is derived from issues_by_vote_2026.json, fetched fresh when the page loads. Each row in that file is one recorded vote action on a file at a specific meeting body — not one unique piece of legislation. The same FileNumber commonly appears more than once: once when a committee votes to recommend it, and again when the full City Council votes on it (sometimes more than once, across readings). That's the whole reason the Dashboard tab's headline "issues" count is so much bigger than the number of distinct files actually considered this session.

Heads up: the "Close votes" quick-filter pill on the Voting Record tab uses a different threshold than the KPI card above — the card requires a margin ≥ 6 (7–6 or tighter), while the pill uses margin ≥ 4 (as loose as 9–4). That's deliberate, not a bug, but it's why the two counts won't match.
Member leaderboard & activity cards
Three per-member tallies feed both the "Most/Least" leaderboard cards and the Member Activity grid on the Dashboard tab.
TallyDefinition
AuthoredRows where AuthorName equals this member. Most rows have no author recorded at all.
DissentRows where the member cast Aye/Nay against whichever side had more votes, restricted to rows where both an Aye and a Nay were cast (unanimous rows can't produce a dissent). Absent/Abstain never counts.
AbsentRows where the member's recorded vote is exactly "Absent".

'Aye' : 'Nay'; for (const [member, vote] of Object.entries(issue.Votes)) { if ((vote === 'Aye' || vote === 'Nay') && vote !== majority) dissentCount[member]++; } });
The four leaderboard cards (Most Authored, Most Dissents, Least Authored, Most Absent) take the max/min of these same three tallies across all 13 members — same underlying numbers as the Member Activity cards, just surfaced as a highlight.
Council Wards map
Ward boundary polygons come from Minneapolis's official open data portal — the City Council Wards ArcGIS FeatureServer, adopted March 2022 — saved locally as ward_boundaries_2026.geojson so the dashboard doesn't depend on that service staying up. Each ward polygon's BDNUM property is matched to a member's ward number to place their photo marker.
The marker isn't placed at the polygon's bounding-box center — that can land outside an irregularly-shaped ward. Instead each marker sits at the ward's true area-weighted centroid:
function ringCentroid(ring) { // ring = [[lng,lat], [lng,lat], ...] let x = 0, y = 0, area = 0; for (let i = 0; i < ring.length - 1; i++) { const [x0, y0] = ring[i], [x1, y1] = ring[i + 1]; const cross = x0 * y1 - x1 * y0; area += cross; x += (x0 + x1) * cross; y += (y0 + y1) * cross; } area *= 0.5; return [x / (6 * area), y / (6 * area)]; }
The basemap is CARTO's dark tile set (dark_all) via Leaflet — no API key required, chosen to match the dashboard's dark theme rather than for any data reason.
